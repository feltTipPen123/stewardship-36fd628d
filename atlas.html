00

Orientation: how a responsibility actually fires

// two tiers, one durable queue, one turn loop

Everything in this tour sits on one spine. A trigger (clock, event, or human) puts a row on a durable Postgres queue; a worker claims exactly one; that becomes a single anima turn; the turn re-derives its world from context and posts. Hold this picture and every stop slots into it.

▣
The one sentenceA responsibility today is a scheduled_tasks row that a clock turns into a dispatch_jobs row that a worker turns into one runAnimaTurn. There is no object that survives across fires except the chat itself.

Four tables matter here, and the most important fact is how little the duty row carries. Learn these shapes cold — the redesign is mostly a change to the first one.

① scheduled_tasks — the duty ledger

② dispatch_jobs — the durable work queue

▸ ③ & ④ — anima_tasks (work tracker) and the vestigial tasks table
⚠
InvariantsSchema changes are expand/contract: additive migrations in drizzle/, destructive in drizzle-contract/, both registered in their _journal.json. Never drizzle-kit push. schema.ts is a shared-pain file — announce before editing. idempotency_key must stay globally unique per logical fire.
△
Where the proposal landsP1/P2. The duty row grows a charter, acceptance, compact state, real status, adaptive nextWakeAt (finally written), triggers, budget; a new append-only responsibility_beats ledger retires the dead checkpoint fields. Additive first — contract the old columns later.
02

The durable queue

// packages/chat-core/src/dispatch-jobs/enqueue.ts + apps/dispatch-worker/src/dispatch-jobs/worker-loop.ts

This is the spine any new wake-path must ride. Do not call runAnimaTurn directly from a trigger — enqueue a job, or you lose durability. Two routines: enqueue (with dedup) and claim (with exactly-one semantics).

⚠
InvariantsEvery wake must enqueue (durability + crash recovery). Idempotency keys must be unique per logical fire — cron uses a time-stamped key so each tick is distinct; one-shots use a stable key so retries dedup. A new trigger_kind needs a matching validator (trigger-validators.ts) or the worker can't route it. chat-core is a shared-pain, cross-tier package.
△
Where the proposal landsP3/P6. New event wakes enqueue here with an existing or new trigger_kind; adaptive next-wake re-enqueues a scheduled job at nextWakeAt. The durable queue is reused as-is — this is the "don't build a workflow engine" guarantee.
03

The scheduler — where the clock lives

// apps/dispatch-worker/src/services/scheduler.ts (note: a second scheduler.ts exists in ws-edge)

In-process node-cron jobs + setTimeout timers, hydrated from the DB at boot. A Redis leader-lock makes sure only one replica fires a given tick. This is the entire "self-scheduling" surface the proposal reframes.

⚠
InvariantsThe anima cannot pick its own wake instant — it can only set cronExpression/runAt and trust the tick. Timers are in-memory: a deploy re-hydrates from the DB, so durable state must be the DB row, never the timer. Leader-lock keys gate multi-replica firing.
△
Where the proposal landsP3/P5. Add an adaptiveWake() path that honours nextWakeAt instead of forever-cron, plus a low-frequency heartbeatBeat() that loads state and decides "act or sleep?" Cron stays for genuinely periodic duties. This file is the natural home for the new wake logic.
04

The event-trigger system

// apps/dispatch-worker/src/services/scheduler-event-triggers.ts

There is exactly one "wake on a signal rather than the clock" mechanism today: dispatch-complete waiters. Understand it before adding new event triggers — the goal is to extend this pattern, not duplicate it.

▣
What this tells you"Events" in bolter currently means "another dispatch finished." There is no first-class subscription to inbound email, a calendar change, or a threshold crossing — though webhook and email trigger kinds already exist on the queue (Stop 02), so the inbound plumbing is partly there.
△
Where the proposal landsP3. Generalise this fan-out into a registerEventTrigger() that matches a responsibility's declared triggers against signals we already capture in-process (and the existing webhook/email kinds) — explicitly not a second source for events we already see.
05

The scheduled-job handler — the smoking gun

// apps/dispatch-worker/src/dispatch-jobs/run-scheduled-job.ts

This is where a claimed scheduled job becomes an anima turn. Read the message it synthesizes carefully: the runtime hands the anima a prose pep-talk about surviving its own context loss, because there is no state object to lean on. This single block is the strongest argument for the whole redesign.

▣
Read this twice"surviving context loss" and "if you decide not to persist state, just don't" are the system admitting the two forces from the proposal. Memory across fires is the anima's manual problem; the runtime offers encouragement, not a charter or a ledger.
△
Where the proposal landsP1/P2/P4. This handler becomes run-beat: re-ground from charter + state + last-K ledger, do a short beat, run the fresh-lens assessment, append a ledger entry, update compact state, and decide the next wake. The prose paragraph is replaced by structure.
06

The turn loop — what a "beat" runs inside

// apps/dispatch-worker/src/services/dispatch/ — run-anima-turn.ts, agent-loop.ts, model-selection.ts, dispatch.ts

Every fire ultimately runs one runAnimaTurn: acquire the group lock, mint IDs, build context, run the agent loop (bounded + loop-guarded), post, then wake any waiters. A "beat" is this, with better grounding around it.

▸ Execution class + the decline-response strip (model-selection.ts, dispatch.ts)
⚠
InvariantsAn anima always responds on a turn (fail loudly: post an anima-voice apology, never go silent). Sequential-group lock is held for the entire turn — don't bypass it. IDs minted pre-dispatch anchor ordering + streaming. MAX_TURNS and the loop detector are safety rails, not progress signals.
△
Where the proposal landsP4/P6. "Beats stay short" means keeping turn counts low and context small — working with these rails. The fresh-lens assessment runs as its own clean-context turn (or sub-agent), distinct from the loop-detector's mechanical repetition guard.
07

Context assembly — the re-grounding surface

// apps/dispatch-worker/src/redis/client.ts + services/dispatch/index.ts + packages/anima-core/src/system-prompt.ts

This is the entire world a fire sees, and where "re-ground from durable state" has to fit. Eight parallel fetches, a hard 50-message window, and a filter that decides which duties even appear in the prompt.

▸ How it renders into the system prompt (anima-core)
⚠
InvariantsA fire that skips buildAnimaContext sees no duties at all. The 50-message window means chat is not reliable cross-fire memory — this is the decay function in code. redis/client.ts (CORE_TOOLS) is a shared-pain file.
△
Where the proposal landsP2. Add the responsibility's charter + acceptance + compact state + last-K ledger as a high-priority prompt block (recitation, at the top) sourced from the durable row — small, fixed-size, and independent of the 50-message window.
08

Tools & the registration ritual

// apps/dispatch-worker/src/tools/ — scheduling.ts, index.ts; packages/shared/src/permissions.ts

The anima edits its own duties through three tools. Adding the proposal's ~5 new tools is mechanical but guarded: a drift test enforces registration in three places. Get the ritual right or CI blocks you.

⚠
Invariants (the registration ritual)A new tool must be (1) added to getAllTools(), and (2) classified in one of TOOL_CAPABILITY_MAP + CAPABILITY_METADATA + DEFAULT_GRANTS (grant-gated), INTRINSIC_TOOLS (audited, no grant), or UNGATED_BY_DESIGN. Tools returning secrets set sensitiveResult:true. The tool-drift.test.ts enforces all of this. tools/index.ts is a shared-pain file.
△
Where the proposal landsP1/P4/P5. New tools — bolter_set_charter, bolter_update_responsibility_state, bolter_set_next_beat, bolter_watch_event, bolter_escalate_to_owner — register exactly like the scheduling tools, gated under a scheduling.manage-style capability.

If you read five files first

// the fastest path to a correct mental model

1

dispatch-jobs/run-scheduled-job.ts

Start at the smoking gun (Stop 05). It shows what a duty fire actually is today and why the redesign exists — the prose substitute for state.

2

services/scheduler.ts

The clock: init → scheduleTask → fireTask → enqueue. This is the surface P3/P5 reshape; know it before adding adaptive/event wakes.

3

chat-core/dispatch-jobs/enqueue.ts + worker-loop.ts

The durable spine + exactly-one claim. Every wake path rides this; it's reused untouched, so understand its guarantees, don't reinvent them.

4

services/dispatch/index.ts + anima-core/system-prompt.ts

How duties enter the model's context and how thin that signal is. This is where re-grounding (P2) has to fit.

5

services/dispatch/run-anima-turn.ts

The turn a beat runs inside: locking, ID minting, the fire-the-waiters seam. Plus the limits in dispatch-budget.ts / loop-detector.ts.

Pre-change checklist

  • New wake path enqueues via enqueueDispatchJob — never calls runAnimaTurn directly.
  • Idempotency key is unique per logical fire (timestamped for recurring, stable for one-shot).
  • New trigger_kind has a matching trigger validator.
  • Committed fires set mustDeliverVisibleReply appropriately; an anima always responds.
  • Re-grounding block is fixed-size and independent of the 50-message window.
  • New tools pass the drift test (registry + capability + sensitiveResult).
  • Migrations are expand/contract, registered in _journal.json; no drizzle-kit push.
  • Announce shared-pain file edits; open a PR; add PostHog events; update docs/.
  • Tests cover: re-fire dedup, stale-task filtering, sequential lock held, dispatch-complete fan-out.
